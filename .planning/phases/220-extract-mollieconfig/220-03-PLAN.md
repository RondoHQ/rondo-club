## Webhook flow under test

Per `./CLAUDE.md`, the Mollie webhook has 4 routing paths (0a, 0b, 1, 2). This test exercises **Path 0b** (full payment link, `pl_xxx`, lookup by `_mollie_payment_link_id`) because `MolliePayment::create_payment_link()` creates a full payment link (not an installment payment link). The reverse-lookup meta key written is `_mollie_payment_link_id` on the invoice (NOT `_mollie_pid_{pl_xxx}` which is for installment plans).

**Meta-key verification reference** (cross-checked from includes/class-mollie-payment.php line 130 and class-mollie-webhook.php lines 88-129):
- Discipline/full invoice via `MolliePayment::create_payment_link()` -> `update_post_meta($invoice_id, '_mollie_payment_link_id', $payment_link->id)` -> webhook Path 0b lookup by `_mollie_payment_link_id`.
- Installment via `InstallmentPaymentService::create_payment()` -> `_mollie_pid_{pl_xxx}` meta -> webhook Path 0a reverse-lookup.

This plan exercises Path 0b, so the evidence MUST assert the `_mollie_payment_link_id` key specifically.

**Test invoice type: discipline** (manual invoice type). Reasoning: discipline invoices use `MolliePayment::create_payment_link()` which is the simplest code path to test (Path 0b webhook, no installment state machine). Membership invoices go through the public payment page + plan selection first, which adds complexity. Testing discipline invoice covers MolliePayment + MollieWebhook + FinanceServices::mollie() -> the three most critical Mollie classes.
