## Webhook flow under test

Per `./CLAUDE.md`, the Mollie webhook has 4 routing paths (0a, 0b, 1, 2). This test exercises **Path 0b** (full payment link, `pl_xxx`, lookup by `_mollie_payment_link_id`) because `MolliePayment::create_payment_link()` creates a full payment link (not an installment payment link). The reverse-lookup meta key written is `_mollie_payment_link_id` on the invoice (NOT `_mollie_pid_{pl_xxx}` which is for installment plans).

Clarification for the must_have "reverse-lookup `_mollie_pid_{pl_xxx}` meta is found": the ROADMAP success criterion uses the reverse-lookup phrasing somewhat loosely. For a discipline/manual invoice with `create_payment_link()`, the meta key is `_mollie_payment_link_id` and the value is `pl_xxx`. For an installment plan, the meta key is `_mollie_pid_{pl_xxx}` and the value is the installment number. EITHER form of reverse-lookup is valid evidence of a clean roundtrip. Document whichever you observe.

**Test invoice type recommendation: discipline** (manual invoice type). Reasoning: discipline invoices use `MolliePayment::create_payment_link()` which is the simplest code path to test (Path 0b webhook, no installment state machine). Membership invoices go through the public payment page + plan selection first, which adds complexity. Testing discipline invoice covers MolliePayment + MollieWebhook + FinanceServices::mollie() → the three most critical Mollie classes.
